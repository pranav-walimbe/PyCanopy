# SpatialBench

This harness measures how PyCanopy performs on
[Apache SpatialBench](https://github.com/apache/sedona-spatialbench), and how that compares against
DuckDB, SedonaDB, and GeoPandas on the same queries and hardware. It provisions the cloud machines,
runs the suite on each engine, and collects the timings into a single chart and report.

## Usage

Needs AWS credentials with EC2 + S3 permissions. `--group bench` supplies the launcher's `boto3`
and `matplotlib`.

```bash
# Compare engines across all queries
uv run --group bench python -m bench.spatial_bench --scale-factor 1 \
  --engine pycanopy duckdb sedonadb geopandas

# One engine, explicit repetition count
uv run --group bench python -m bench.spatial_bench --scale-factor 10 --engine pycanopy --n 3

# Single query, for debugging
uv run --group bench python -m bench.spatial_bench --scale-factor 1 --engine pycanopy --query q12

# Profile + verify (SF1 only, PyCanopy only, takes no other flags)
uv run --group bench python -m bench.spatial_bench --profile
```

The launcher starts one EC2 instance per node, polls them concurrently, combines their transport
files, and terminates every instance when done. Ordinary runs fan out over engines and write one
grouped PNG and one text report. `--profile` fans out over builds of PyCanopy instead, and writes
`assets/profile.txt`.

## Methodology

- **Pinned inputs:** workload revision `b9221a9c4b02b10db20611d79b4019d2b3c4b68e`, official dataset
  `v0.1.0` at SF1 or SF10, and the upstream reference answers generated by canonical SedonaDB
  queries.
- **Dataset source:** a public-read mirror of the upstream Hugging Face dataset
  (`apache-sedona/spatialbench`, `v0.1.0`) in `s3://pycanopy-bench-data`, `us-west-2`. Upstream
  publishes its pre-generated data only on Hugging Face and its CI verifies against that build, so
  it is the one the committed answers correspond to. Apache's own published single-node chart reads
  a different build in `wherobots-examples`, whose synthetic keys and building footprints do not
  match those answers, which is why the mirror exists.
- **Hardware:** one ephemeral **m7i.2xlarge** (8 vCPU, 32 GB, `us-west-2`) per engine, launched
  concurrently on identical infrastructure.
- **Timed S3 reads:** queries read projected Parquet columns straight from the public dataset in
  `us-west-2`, never staged locally. Timings include those reads, matching Apache's published
  single-node methodology.
- **Process isolation:** every query runs in a fresh subprocess, so no index, object, or cache is
  reused between queries.
- **Engine releases:** ordinary runs install the latest PyPI release of each engine and record the
  exact versions in the report. Profile mode builds PyCanopy from the configured branch instead.
- **Repetitions:** `--n` runs per query (default 3), each in its own subprocess. A partial sample
  set is invalid. Each attempt gets the published 1,200 second limit.
- **Run metadata:** the report records timestamp, workload, dataset, engine version, query
  configuration, system/CPU details, and cloud/EBS configuration. Custom source paths are never
  written.

## Profiling

`--profile` runs SF1 once per query and reports total wall time, sampled RSS against baseline,
PyCanopy's own Engine metrics (per-index build cost and per-operation compute nanoseconds), and a
verdict against the committed answer.

Engine times are exact Rust compute; everything else, parquet reads included, falls into
`non-engine wall`. Ordinary runs are timing-only.

### Comparing against the last release

A profile run launches **two** instances concurrently, both `m7i.2xlarge` in `us-west-2`:

| variant | PyCanopy under test | how it is installed |
|---|---|---|
| `branch` | `repository_branch` | Rust toolchain plus `maturin develop --release` |
| `release` | latest published wheel | `uv pip install pycanopy` |

Both clone the same branch, so both run **identical query code** and the difference between them
is the library alone. A change to a query under `queries/pycanopy/` therefore moves both columns
and does not appear as a delta.

Running them side by side is the point. A single profile compared against an earlier one confounds
the code change with whatever the machine and the S3 read path were doing that day, and one run
per query gives no variance estimate to separate them. Two concurrent boxes meet the same
conditions, so the delta between the columns is attributable.

`assets/profile.txt` then carries a run metadata block, a per-query wall and peak comparison with
percentage deltas, a per-query engine breakdown by stage, and the full per-query detail for the
branch build. Each box also uploads its own `assets/profile-<variant>.{txt,json}`, the second of
which is the machine-readable payload the launcher combines.

The released build is a baseline, not the thing under test. If it fails or mismatches, that is
recorded and the run still reports; only a failing branch build fails the run. A query the
released wheel cannot run at all, because the branch uses an API it does not have, shows as
`no profile from the released build`.

Verification compares against the committed upstream answer, with the answer Parquet's schema
controlling comparison types. Integer keys, strings, timestamps, and row order must match exactly;
floats use upstream tolerances, including the duration and final-row boundary rules in
`answers/README.md`.

## IAM setup

The EC2 instance uses an instance role, no injected keys. It needs `s3:PutObject`/`s3:GetObject`
on the results bucket in `config.py`, plus `s3:ListBucket` on that bucket. The dataset is
public-read, so queries reach it anonymously and need no grant. The local launcher additionally
needs SSM read, EC2 lifecycle, `iam:PassRole`, and results-bucket read.

## Directory layout

Code splits by where it runs. On-box code executes on EC2 from a fresh clone of
`repository_branch`, so **on-box changes only take effect once pushed**, and an ordinary run
installs only the measured engine's own packages.

```
bench/spatial_bench/
├── __main__.py       # local: launch, monitor, and combine isolated engine nodes
├── config.py         # workload, dataset, engine, path, timing, and infrastructure settings
├── driver_utils.py   # on-box: drive one engine over the queries, timed or profiled
├── run_query.py      # on-box: isolated subprocess running exactly one query
├── profiler_utils.py # on-box: stage boundaries, sampled RSS, Engine metrics, verification
├── report_utils.py   # the TSV transport (both sides) plus text, chart, and profile reports
├── answers/          # pinned upstream CSV and type-faithful Parquet answers
├── bootstrap.sh      # EC2 user-data: install one engine and run its suite
├── queries/          # pycanopy/ duckdb/ sedonadb/ geopandas/, q01.py through q12.py each
└── engines/          # pycanopy/ duckdb/ sedonadb/ geopandas/ execution adapters
```
